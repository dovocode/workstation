Workstation / Product & engineering plan / 06 September 2026

A dependable foundation for every workstation.

Evolve the tool from a package reconciler into a predictable system for software, configuration, environments, secrets, and services.

Proposal, not an implementation commitment. New APIs below are illustrative. Phase estimates are planning ranges for one experienced engineer, not delivery dates.

01 / Product direction

Make every change understandable and recoverable.

The common experience

Declare a desired setup, preview exact changes, apply it, and inspect its status. Every resource uses the same identity, dependency, diff, ownership, and reporting model.

Respect backend differences

Offer consistent commands across managers without pretending that exact versions, downgrade, offline operation, or rollback work identically. Capability checks produce an actionable explanation before mutation.

Starting point

The conversation establishes a published 0.1.2 baseline with multiple package backends, locks, native builds, and prerequisite bootstrapping. Local work adds explicit build, self-update, bounded concurrent reads, quieter logging, and marked file injection. Treat these local changes as candidates requiring review before release.

First release gate: configuration-scoped state. A temporary configuration previously reused the real workstation state and caused unintended restoration. Isolate state, tie plans to a configuration identity, and isolate all executable tests before broadening the resource set.
02 / Technical foundation

One engine. Explicit resource capabilities.

  1. Load and validate: resolve machine/profile selections, duplicate targets, secret references, and resource identifiers.
  2. Inspect: bounded, read-only queries with shared manager metadata and cancellation.
  3. Plan: immutable actions, file diffs, dependency order, backend limitations, and preconditions.
  4. Apply: validate plan freshness, journal intent, execute mutations under manager locks, verify results, and checkpoint.
  5. Recover: report completed and pending actions; restore supported file changes or propose compensating package actions.

Core contracts

ComponentResponsibilityAcceptance rule
Configuration identityStable ID plus canonical source path; state namespace, explicit import/migration command.Two configurations cannot remove each other's resources; overlapping targets are detected.
Resource adapterValidate, inspect, diff, apply, verify, remove, capabilities.Unsupported operations fail during planning; inspection does not mutate.
Dependency graphExplicit dependencies, cycle detection, reverse removal order.Services cannot start before required files and packages are verified.
SchedulerSeparate read/write limits, per-manager mutation locks, timeouts, cancellation.Independent reads overlap; state commits remain serialized.
State and journalVersioned schema, pre-run snapshot, atomic commits, recovery records.A crash between mutation and commit can be diagnosed and resumed without duplicate destructive work.
Event streamTyped phase/action/progress/error events rendered as human output or JSON.Verbose details never require regex filtering of human messages.

Do not expose a general third-party adapter API until two internal adapters share a stable contract. Avoid global mutable PATH changes where a per-run execution environment can express the same dependency.

Capability negotiation

Each adapter reports support or constraints for exact install, upgrade, downgrade, uninstall, batching, offline reads, bootstrap, and recovery. A plan must distinguish “supported,” “conditional,” and “unsupported,” with the reason and remediation. Recovery is not a universal package rollback guarantee.

Efficient reads, controlled writes

Batch installed inventory and version metadata where possible. Cache within a run using manager, scope, repository state, and package identity; invalidate affected entries after writes. Keep configurable bounded concurrency and per-manager locks. Recheck destructive preconditions immediately before execution.

04 / Configuration & environments

Dotenv becomes a first-class resource.

PolicyProposed contract
updateRetain current ownership-sensitive behavior; document when unmanaged differences are rejected.
overwriteManage whole-file contents; retain original bytes and permissions for guarded restoration.
ignorePreserve an existing target; clearly show that its differences are intentionally unmanaged.
injectOwn an explicit marker-delimited section, preserve outside edits, reject ambiguous boundaries; support named blocks through one file resource.
mergeOwn declared keys/paths only; preserve unrelated content. Restore original owned keys only if their current values still match the last managed values.

Dotenv specification

  • Parse without sourcing or executing the file. Preserve literal dollar signs and command-substitution text by default.
  • Define supported quoting, escapes, export prefixes, empty values, multiline values, comments, BOM and line endings; reject unsupported syntax with line/column errors.
  • Detect duplicate keys; require an explicit policy instead of silently editing one occurrence.
  • Use a deletion sentinel for explicit deletion. Omitted keys remain untouched in merge mode.
  • Preserve ordering and comments; append new keys predictably; a second build must produce no diff.
  • Add required-key schemas, defaults, allowed values and typed checks. Generate examples with placeholders rather than secrets.
  • Define precedence: shared defaults → selected profile → machine overrides → explicit invocation overrides. Keep interpolation opt-in and separate from secret resolution.

Secret handling is part of the design

Support environment and file references first; add external providers later through adapters. Resolve secrets during apply, redact diffs and logs, and keep resolved values out of committed locks and plain manifests. Encrypt sensitive recovery snapshots or require an explicit no-backup policy. Plain hashes are insufficient protection for low-entropy secrets.

Beyond dotenv

Add format-aware JSON/JSONC, YAML, TOML and INI patches; text templates; copies, directories and permissions; Git conditional includes; SSH Host sections; shell exports and PATH entries; editor settings and extensions. Preserve syntax using format-aware representations, and reject unsupported edits rather than silently stripping comments.

05 / Delivery sequence

Ship in layers with measurable exit gates.

Rough engineering effort: 16–27 engineer-weeks for the core phases below, before contingency, external-provider work, and ongoing platform maintenance. Re-estimate after the first two phases.

00

Stabilize the current branch · 1–2 weeks

Review local CLI, injection, bootstrap, concurrency and update changes. Introduce test-only state/home roots. Reserve built-in command names consistently and correct stale examples. Audit self-update detection, artifact validation, temporary files, version comparison and installation-channel behavior.

Exit: isolated end-to-end tests cover help, build, update failure, injection restore and interruption. No test can access the real user's state or package managers.

01

State ownership and recovery · 2–3 weeks

Add configuration namespaces, target conflict checks, explicit legacy-state migration, snapshots, an operation journal and guarded restore. Preserve adopted-vs-owned semantics; do not infer ownership during migration.

Depends on: 00. Exit: two configurations remain isolated; forced termination at every journal boundary is recoverable; restore preserves unrelated later edits.

02

Plan, diff and execution contracts · 2–3 weeks

Separate planning from lock writes and bootstrap mutations. Add plan/status/doctor, structured events, stable exit codes, frozen-lock builds, selection and no-remove mode. Bind saved plans to config and state fingerprints.

Depends on: 01. Exit: plan produces zero filesystem/process mutations; stale plans fail with an explanation; secret-bearing differences are redacted.

03

Backend parity and scheduling · 3–5 weeks

Implement adapter capabilities and dependency scheduling, bulk inventory, cache invalidation, per-manager locks, retries for safe reads, timeouts, and cancellation. Build a contract suite for every supported backend.

Depends on: 02. Exit: every backend implements the common workflow or a clear capability rejection; mutations cannot race within one manager; benchmark results are recorded.

04

Dotenv, merge and secrets · 3–5 weeks

Ship the dotenv parser and key ownership model, environment/file secret references, schema validation, preview redaction and secure recovery. Extend to JSON/JSONC first; add YAML/TOML/INI only after comment-preserving behavior is tested.

Depends on: 01–02; can overlap 03 after contracts stabilize. Exit: round-trip fixtures preserve unowned bytes, generated examples contain no secrets, conflicts do not overwrite external edits.

05

Developer environment resources · 3–5 weeks

Add Git repositories, verified downloads and archives, templates, file/directory resources, SSH/Git configuration, task dependencies and service health checks. Apply explicit dependency edges to service restarts.

Depends on: 03–04. Exit: an example application installs, receives its environment, starts, passes health checks, and converges on a second build.

06

Release and usability finish · 2–4 weeks

Add completions, run history, profile discovery, installation-channel updates, signed/checksummed release artifacts, migration guides and offline diagnostics. Publish realistic sample configurations and a tested support matrix.

Depends on: previous release gates. Exit: clean-machine installs and upgrades pass on supported architectures; documentation examples run in CI; recovery limitations are explicit.

Shared selectors: --config, --machine, --profile, --only, --exclude. Build controls: --frozen-lockfile, --no-remove. Output: --json, --quiet, --verbose. Define selection as a projection of the full plan so excluded resources are never treated as removed.

07 / Verification & operational targets

Measure correctness before speed.

Correctness gates

  • Second build: zero changes and stable generated bytes.
  • Plan/status: no mutation, including installers, lock updates and file writes.
  • Cross-config deletion: blocked in every regression case.
  • Interruption: recoverable state at each execution boundary.
  • Merge/injection: retain unrelated edits on apply and restore.
  • Secrets: no plaintext in logs, diffs or committed artifacts.

Performance targets to validate

  • Record baseline cold/warm wall time and spawned-process counts for 25, 100 and 250 resources.
  • Target at least 50% fewer metadata subprocesses for a representative 100-package bulk-query workload.
  • Target at least 30% lower warm read-phase time on the same machine and network conditions.
  • Keep bounded memory and process counts; cancellation stops new scheduling immediately.
  • Emit progress at least every five seconds during long phases without repeated per-query noise.

Targets are acceptance goals, not measured claims. Use unit/property tests for parsers and graph logic, adapter contract fixtures, Linux disposable environments, and dedicated macOS test runners. Interactive backends require a separately documented manual verification track. Test release upgrades against fixture servers and disposable executable copies.

Release discipline

Review schema migrations and behavior changes before tagging. Attach checksums and provenance to native artifacts; validate architecture and expected version before replacement. Keep previous binaries for bounded recovery. Mark API changes and unsupported capabilities clearly, and validate examples as part of release CI.

Decisions to settle during phase 00

  • Choose stable configuration IDs and a deliberate migration rule for existing global state.
  • Decide whether build keeps current automatic lock refresh or requires explicit refresh by default; always offer frozen execution.
  • Define one documented dotenv dialect and secret-backup policy.
  • Choose supported minimum OS/runtime versions and the maintained backend test matrix.
  • Choose whether recovery is an interactive preview or a plan artifact followed by explicit apply; never imply universal rollback.
First milestone: a user can preview a scoped setup, understand the diff, apply it, interrupt it, recover it, and run it again with zero changes. Dotenv and richer resource types then inherit those guarantees.
